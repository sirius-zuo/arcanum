Arcanum Architecture Specification

Version: 1.2 | Date: May 2026 | Positioning: High-Performance Rust RAG Knowledge Engine

1. Overview & Positioning

Arcanum is an independent, high-performance RAG knowledge engine framework focused on document ingestion, vector storage, and intelligent retrieval.

It serves as the foundational knowledge layer for ArcVerse (the Agentic RAG product), and provides standardized access via the MCP protocol.

Additionally, it provides a team-facing admin portal for ingestion management, retrieval configuration, system monitoring, and operational control — useful in both production and development environments.

Design Principles

  • Highly modular and Trait-driven design
  • Production-ready (async, high concurrency, observability)
  • Supports both library mode and MCP service mode
  • Keeps purity: Does not include Agentic logic (handled by ArcVerse)
  • Team operations: Admin portal for ingestion/retrieval management, system health monitoring, and audit (production and development)

3. Detailed Module Design

3.1 arcanum-core (Foundation Layer)

Positioning: The cornerstone of the entire framework, providing public definitions, abstractions, and anti-corruption boundaries.

Core Responsibilities:

  • Define all core Traits and data structures
  • Provide unified configuration system (ArcanumConfig)
  • Centralized error handling and Result types
  • Common utilities (serialization, timing, tracing, metrics)
  • Version management and Feature Flag control
  • Secrets management abstraction (SecretStore trait for loading API keys, DB credentials, JWT keys)

Key Components:

  • Core Types: RawDocument, Chunk, IndexedChunk, RetrievedChunk, Query, MetadataFilter
  • Traits: DocumentLoader, Chunker, Embedder, VectorStore, Retriever, Reranker, SecretStore
  • Configuration System: Layered config (Global, Ingestion, Retrieval, Storage, Admin)
  • Observability Primitives: Tracing spans and Metrics definitions
  • SecretStore Trait: Abstracts credential loading (env vars, vault, cloud secrets manager)
  • Anti-Corruption Layer: Adapter traits that translate external API types into Arcanum domain types

Design Considerations:

  • Keep extremely lightweight with minimal dependencies
  • Strong typing + Builder Pattern for better usability
  • Unified async interface using async_trait
  • High extensibility for future features
  • External API models (vector store responses, embedding provider errors) must never leak into pipeline or core modules — all translated via anti-corruption adapters
  • Secrets are loaded through the SecretStore trait at startup, never hardcoded
Review Finding — CircuitBreaker Cohesion: The CircuitBreaker pattern was previously listed in arcanum-core but is a generic infrastructure concern, not a RAG-specific abstraction. It has been moved to arcanum-middleware (a new crate) to keep arcanum-core focused on RAG domain abstractions. The arcanum-middleware crate also contains the BoundedQueue pattern (used by the ingestion pipeline). arcanum-core re-exports these via its public API for convenience. This addresses the concern that arcanum-core was becoming a "trait library" rather than a focused domain layer.

3.2 arcanum-ingestion (Document Ingestion Layer)

Positioning: Responsible for ingesting raw data sources and transforming them into structured, indexable Chunks. In production mode, ingestion operates asynchronously via a background worker queue.

Core Responsibilities:

  • Support multiple data source loading
  • Document cleaning and preprocessing
  • Intelligent chunking strategies
  • Automatic metadata extraction and enrichment
  • Incremental ingestion (process only changed content via document hash tracking)
  • Ingestion source configuration management (tracked via admin portal)

Key Components:

  • Loaders (PDF, Markdown, Database, Notion, ePub, etc.)
  • Preprocessors (HTML Cleaner, Table Extractor, Image Captioner)
  • Chunkers (FixedSizeChunker, SemanticChunker, HierarchicalChunker, StructureAwareChunker)
  • Metadata Extractors (Title, Keywords, Entities, Hierarchy, etc.)
  • DocumentHashTracker (incremental ingestion — detects changed content)
  • IngestionTask (internal DTO for async worker queue)
  • IngestionSourceConfig (admin-tracked configuration for data sources: source type, URI, schedule, collection mapping)

Design Considerations:

  • Chunks must carry rich metadata for advanced filtering
  • Pluggable pipeline architecture for custom processors
  • High robustness and error recovery during ingestion
  • All input from document loaders is validated and sanitized before processing (prevents injection via malicious file content)

3.3 arcanum-embedding (Embedding Layer)

Positioning: Unified text vectorization layer.

Core Responsibilities:

  • Embedding model invocation
  • Batch processing and parallel execution
  • Vector post-processing and normalization
  • Multi-vector embedding support

Key Components:

  • Embedder implementations (Local TEI, OpenAI, Ollama, BGE, etc.)
  • EmbeddingCache (optional Redis-based, with key-based invalidation)
  • MultiVectorStrategy (summary + full text vectors)
  • EmbeddingParallelismRouter (routes embedding requests across multiple service instances — round-robin for TEI, batch-split for OpenAI)

Design Considerations:

  • Seamless switching between local and cloud embedding services
  • Strong focus on embedding cost control (batching, caching, quantization)
  • Configurable model dimension and version management
  • Parallelism strategy: When multiple embedding service instances are available (e.g., multiple TEI servers), the EmbeddingParallelismRouter fans out requests using round-robin scheduling. For cloud providers with per-request limits (e.g., OpenAI), the router splits large batches into sub-batches with rate-aware pacing.
Review Finding — Embedding Parallelism: The v1.1 spec mentioned "batch processing and parallel execution" but did not specify how parallelism is managed across embedding service instances. A single embedding API endpoint becomes a sequential bottleneck even with async ingestion. The EmbeddingParallelismRouter component addresses this by distributing embedding requests across multiple service instances or splitting batches across rate-limited endpoints.

3.4 arcanum-storage (Storage Layer)

Positioning: Persistent storage management for chunks and vectors.

Core Responsibilities:

  • CRUD operations for vector data
  • Metadata filtering and hybrid indexing
  • Collection management and isolation
  • Index maintenance and optimization

Key Components:

  • VectorStore abstraction with multiple backends
  • CollectionManager for multi-knowledge-base support
  • HybridIndexManager (Vector + BM25)
  • MetadataStore (PostgreSQL for production; SQLite for development/prototyping only)

Design Considerations:

  • Transactional writes with rollback capability
  • Configurable consistency levels
  • Support for index rebuilding, merging, and compression
  • SQLite restriction: SQLite is development-only. Production deployments (especially hybrid/multi-node) require PostgreSQL. Build-time feature flags or runtime checks must prevent SQLite in production mode to avoid data inconsistency and write contention.

3.5 arcanum-retrieval (Retrieval Layer)

Positioning: High-precision retrieval core of Arcanum.

Core Responsibilities:

  • Query understanding and transformation
  • Multi-strategy hybrid retrieval
  • Result reranking and post-processing
  • Retrieval quality evaluation
  • Retrieval configuration management (tracked via admin portal)

Key Components:

  • QueryTransformer (Rewrite, HyDE, Multi-Query)
  • HybridRetriever (Vector + BM25 + Metadata Filter)
  • Reranker (CrossEncoder, LLM-based, Score Fusion)
  • ResultProcessor (Deduplication, Citation Generator)
  • Multi-Index Router
  • QueryCache (optional LRU cache, keyed on query fingerprint + collection, TTL-based invalidation tied to document modification timestamps)
  • RetrievalConfig (admin-tracked configuration: retrieval strategy, reranker weights, cache settings, fallback behavior)

Design Considerations:

  • Support parallel retrieval execution
  • Configurable retrieval pipeline (Retrieve → Rerank → Post-process)
  • Results must include traceable citation information
  • QueryCache uses LRU eviction with TTL-based invalidation tied to document modification timestamps to avoid stale results
Review Finding — Cache Invalidation Coordination: arcanum-embedding has an EmbeddingCache (key-based invalidation) and arcanum-retrieval has a QueryCache (TTL-by-doc-modification). These two caches have different invalidation strategies and a dependency chain: if the EmbeddingCache serves stale vectors and the QueryCache serves stale results, the system serves outdated retrieval results. The coordination protocol is: document modified → invalidate EmbeddingCache entries for that document → invalidate QueryCache entries for affected collections. This protocol is documented at the arcanum-core level as a cross-module contract, not an implementation detail.

3.6 arcanum-pipeline (Pipeline Layer)

Positioning: End-to-end workflow orchestration layer.

Core Responsibilities:

  • Provide complete Ingestion Pipeline (async worker-based in production mode)
  • Provide complete Retrieval Pipeline (synchronous, with optional caching)
  • Workflow state management and tracking
  • Generate detailed reports

Key Components:

  • IngestionPipeline (sync API — accepts request and returns OperationId; background worker processes asynchronously)
  • RetrievalPipeline (synchronous with optional query result caching)
  • ArcanumEngine (unified public entry point — thin orchestrator that delegates to pipeline modules)
  • IngestionWorker (tokio-based background worker pool for chunking, embedding, and storage)

Design Considerations:

  • Ingestion is synchronous on accept but asynchronous in processing — prevents large document batches from blocking the service
  • Error recovery with configurable retry policy (exponential backoff with jitter)
  • Graceful degradation: when a dependency is unavailable, return clear errors or fallback behavior (e.g., queued ingestion, stale cached results for retrieval)
  • ArcanumEngine must remain a thin orchestrator — never a monolithic controller with direct knowledge of all components
  • Allow users to insert custom processors in the pipeline
Review Finding — Bounded Ingestion Queue: The design previously specified queuing ingestion when the vector store is unavailable, but did not mention a queue size limit. An unbounded queue under sustained dependency failure could exhaust memory. The ingestion pipeline now uses a bounded queue (via arcanum-middleware::BoundedQueue) with a configurable maximum capacity. When the queue is full, the API returns HTTP 503 with a Retry-After header and a descriptive error message. Default capacity: 10,000 operations (configurable via ArcanumConfig).
Review Finding — Staggered Circuit Breaker Reset: In hybrid mode with multiple retrieval nodes, simultaneous circuit breaker recovery (all nodes probing a recovering service at once) can cause a thundering herd. The circuit breaker implementation uses randomized or jitter-based reset intervals (configurable min/max range, default: 5-15 seconds) to stagger recovery attempts across nodes. The jitter is seeded with node-unique identifiers to ensure each node probes at a different time.

3.7 arcanum-server (HTTP/gRPC Service Adapter)

Positioning: HTTP/gRPC transport layer that wraps arcanum-mcp with a traditional REST/gRPC interface. arcanum-server does NOT implement MCP protocol — it provides an alternative transport for clients that cannot use MCP.

Relationship to arcanum-mcp: arcanum-mcp is the canonical interface (source of truth for all Arcanum capabilities). arcanum-server is a thin adapter that translates HTTP/gRPC requests into MCP protocol calls, reusing the same handlers, session management, and authentication logic from arcanum-mcp. This avoids duplication of auth, rate limiting, and routing logic.

Core Responsibilities:

  • HTTP/gRPC transport layer (using axum or tonic)
  • Delegates authentication, authorization, and business logic to arcanum-mcp
  • Request/response format translation (HTTP JSON ↔ MCP JSON-RPC)
  • Health check endpoints (/health, /ready) for liveness and readiness probes
  • Admin portal serving (static frontend assets + admin API endpoints)

Key Components:

  • HttpServer: HTTP server using axum or gRPC using tonic
  • McpClientAdapter: Translates HTTP requests into MCP protocol calls
  • HealthEndpoint: Liveness probe (internal health) and readiness probe (vector store + embedding service connectivity)
  • RateLimiter: Per-user, per-collection, and global rate limiting (delegates to MCP module's rate limiter)
  • AdminRouter: Routes /admin/* requests to admin handlers (separate auth, elevated privileges)
  • StaticAssetServed: Serves the admin portal frontend (embedded or CDN-hosted)

Route Grouping:

  • /api/v1/* — Public MCP adapter routes (same handlers as arcanum-mcp)
  • /health, /ready — Health probes
  • /admin/* — Admin portal (requires admin JWT, separate auth middleware)
  • /admin/ui/* — Static admin frontend assets (served via ServeDir)

3.8 arcanum-mcp (MCP Service Layer)

Positioning: Canonical service exposure layer using Model Context Protocol (MCP). All Arcanum capabilities are defined here — arcanum-server adapts to this interface, not the reverse.

Core Responsibilities:

  • Implement full MCP protocol (JSON-RPC over SSE/WebSocket)
  • Expose Arcanum capabilities as MCP Resources and Tools
  • Handle session management, resource discovery, authentication, and authorization
  • Provide health check endpoints for service orchestration
  • Manage rate limiting, audit logging, and content safety hooks

Key Components:

  • McpServer: Core MCP server implementation
  • ResourceRouter: Routes requests to appropriate handlers
  • CapabilityRegistry: Dynamic capability registration
  • Request Handlers: SearchHandler, IngestionHandler, CollectionHandler
  • SessionManager & AuthMiddleware
  • HealthEndpoint: Readiness probe (checks vector store, embedding service, metadata DB connectivity)
  • AuditLogger: Structured audit log for ingestion, retrieval, and admin operations

Design Considerations:

  • Strict adherence to MCP specification
  • Collection-level isolation and permission control
  • Support streaming responses
  • High security and auditability
  • Health checks return dependency status so orchestrators can detect and recover from failures
  • Audit log entries include: operation type, user identity, collection ID, timestamp, and result

3.9 arcanum-admin (Admin Portal) — New in v1.2

Positioning: Team-facing admin interface served by arcanum-server, providing ingestion management, retrieval configuration, system monitoring, and audit capabilities. Used by both production operators and development testers.

Authentication: JWT with role-based access control (RBAC). Admin JWT is distinct from user API keys. Three roles:

  • admin — Full access: manage collections, configure ingestion sources, modify retrieval settings, view all audit logs, rotate API keys
  • operator — Read access to monitoring and logs, manage ingestion operations (start/stop/retry/cancel), view collection stats
  • tester — Read access to system health and metrics, manage test collections, run retrieval quality evaluations

Admin API Endpoints:

  • GET/POST/DELETE /admin/collections — Collection CRUD with stats
  • GET /admin/collections/:id/health — Collection health (stale docs, unindexed chunks)
  • GET/POST /admin/ingestion-sources — Ingestion source configuration (source type, URI, schedule, collection mapping)
  • GET/POST/DELETE /admin/ingestion-operations — Ingestion operation management (list, retry, cancel)
  • GET /admin/ingestion-operations/:id — Operation detail (pipeline stage, duration, errors)
  • GET/POST /admin/retrieval-config — Retrieval configuration management (strategies, reranker weights, cache settings)
  • GET /admin/health — Service and dependency health
  • GET /admin/metrics — System metrics (uptime, memory, CPU, throughput)
  • GET /admin/audit-logs — Searchable/filterable audit trail
  • POST /admin/keys/rotate — API key rotation
  • GET/POST /admin/circuit-breakers — Circuit breaker state management

Real-Time Updates: Admin portal uses WebSocket (via SSE fallback for browsers that do not support WS) for real-time ingestion progress updates, circuit breaker state changes, and health status. Clients subscribe to topic-based event streams:

  • ingestion:progress — Real-time ingestion operation progress updates
  • system:health — Dependency health changes
  • system:circuit-breaker — Circuit breaker state transitions
  • admin:audit — New audit log entries (admin role only)

Admin Frontend: Served as embedded static assets (no external dependencies at runtime). The frontend uses vanilla JS with lightweight chart libraries for dashboards. The admin UI is self-contained within the arcanum-server binary via Rust's `include_bytes!` or embedded file system.

Security: Admin endpoints are NOT exposed via the MCP interface (only HTTP). Admin operations are logged with full audit trail (including admin user identity and action details). Optionally, admin access can be restricted to IP allowlists for air-gapped deployments.

4. Ingestion Pipeline Details

flowchart LR
    A[Data Source] --> B[Document Loader]
    B --> C[Preprocessor]
    C --> D[Metadata Extractor]
    D --> E[Chunking Strategy]
    E --> F[Embedding Generator]
    F --> G[Vector Store Writer]
    G --> H[Ingestion Report]

Ingestion Source Configuration: Admin users can configure ingestion sources via /admin/ingestion-sources. Each source defines: source type (file, URL, database, Notion), URI or connection string, schedule (one-time, cron, continuous), target collection, and chunking strategy overrides. The IngestionWorker picks up configured sources and processes them according to schedule. Source changes are applied without restart via the admin portal.

Review Finding — Bounded Queue in Detail: The ingestion pipeline accepts requests synchronously (returns OperationId) and places them into a bounded queue (arcanum-middleware::BoundedQueue). When the queue is full, the endpoint returns 503 with a Retry-After header. The queue depth is exposed via the admin endpoint GET /admin/ingestion-operations (shows pending/processing/failed/completed counts). Operators can adjust the queue capacity via admin API without restart.
Review Finding — Graceful Degradation Detail: When the vector store is unavailable, ingestion operations are placed in the bounded queue with a "waiting" status. The admin portal shows the queue depth and estimated wait time. When the vector store recovers, queued operations resume automatically. When the embedding service times out, the same queue mechanism applies. When the metadata DB is unreachable, reads may use cached collection metadata; writes are queued.

5. Retrieval Pipeline Design

flowchart TD
    Q[User Query] --> QT[Query Transformer]
    QT --> HR[Hybrid Retriever]
    HR --> RR[Reranker]
    RR --> PP[Post Processing]
    PP --> RES[Retrieval Result]

Retrieval Configuration: Admin users can configure retrieval behavior via /admin/retrieval-config. Settings include: which retrieval strategies to enable (vector, BM25, metadata filter), reranker type and weights, cache settings (enabled/disabled, LRU size, TTL), query transformation options (HyDE, Multi-Query), and fallback behavior (e.g., if reranker is unavailable, return raw hybrid results sorted by vector score). All configuration changes are applied without restart and are audited.

Review Finding — Cache Invalidation Protocol: The coordinated invalidation chain is: document modified → (1) EmbeddingCache: invalidate vector entries for that document's chunks → (2) QueryCache: invalidate entries for affected collections. This is implemented as a single atomic operation in the pipeline layer. The QueryCache uses a document-modification timestamp watermark to detect stale entries. The admin portal exposes cache stats (hit rate, size, eviction count) at GET /admin/metrics.

7. Security Considerations

Security is a first-class concern in Arcanum's design, especially when running as an MCP service.

Key Security Features:

  • Authentication & Authorization: API Key, JWT, OAuth2, and fine-grained Collection-level ACLs
  • Admin RBAC: JWT with three roles (admin, operator, tester) for the admin portal — separate from user API keys
  • Data Isolation: Strict tenant/collection isolation to prevent cross-data leakage
  • Input Validation & Sanitization: Comprehensive validation to prevent injection and malicious queries
  • Rate Limiting & Resource Guard: Per-user, per-collection, and global rate limiting (centralized in arcanum-mcp, reused by arcanum-server)
  • Encryption: TLS 1.3 for all communications, at-rest encryption for vector data (mandatory for production, optional for dev)
  • Audit & Compliance: Full operation audit logging with traceable user actions (ingestion, retrieval, admin operations)
  • Content Safety: Optional integration with moderation models during ingestion
  • Least Privilege: MCP Resources follow strict permission model
  • Admin Endpoint Isolation: Admin endpoints are NOT exposed via the MCP interface — only accessible through arcanum-server's HTTP layer
  • IP Allowlist (optional): Admin access can be restricted to specific IP ranges for air-gapped deployments

Threat Model Addressed: Prompt injection, data exfiltration, DoS attacks, unauthorized access, admin privilege escalation, cross-tenant data leakage.

Review Finding — At-Rest Encryption: Previously marked as optional. Now mandatory for production deployments (enforced via feature flag or runtime check). Optional for dev. Backend-specific limitations documented: LanceDB does not support at-rest encryption natively (use encrypted filesystem or volume), pgvector requires tablespace-level or column-level encryption setup.
Review Finding — Rate Limiting Centralization: Rate limiting is centralized in arcanum-mcp. Both arcanum-server and arcanum-mcp share the same limiter instance. If a user connects via the HTTP adapter AND the MCP interface, they are subject to a unified rate limit.
Review Finding — API Gateway Pattern: For production deployments, an API gateway (nginx, Traefik, Envoy) or reverse proxy is recommended in front of arcanum-mcp/arcanum-server. This centralizes TLS termination, rate limiting, auth, and monitoring at the network boundary. The application itself still handles application-level rate limiting (centralized in arcanum-mcp), but the gateway provides an additional layer for DDoS protection, IP-based blocking, and TLS offloading.

8. Cost & Deployment Considerations

Cost efficiency is a core design goal of Arcanum.

Key Cost Optimization Strategies:

  • Embedding Cost Control: Prefer local embedding models (text-embeddings-inference), aggressive batching, and smart caching
  • Storage Optimization: Hierarchical chunking, vector quantization, and smart indexing to reduce storage footprint
  • Compute Efficiency: Leverage Rust's performance advantages and async runtime to minimize CPU/memory usage
  • Incremental Processing: Only re-process changed documents during ingestion
  • Query Result Caching: Optional LRU cache at retrieval layer reduces redundant vector store lookups for repeated queries
  • Deployment Flexibility:
    • Library Mode: Embed directly into applications (lowest cost)
    • MCP Service Mode: Independently scalable microservice
    • Hybrid Mode: Multiple retrieval nodes behind a load balancer

Typical Deployment Cost Models:

  • Small team / Prototype: Local LanceDB + local embedding + SQLite (very low cost)
  • Medium Enterprise: PGVector + dedicated embedding service + PostgreSQL (production-grade)
  • Large Scale: Distributed vector database + GPU-accelerated embedding + Redis cache

Database Requirements by Environment:

  • Development/Prototype: SQLite for metadata store (single-node only, no concurrent writes)
  • Production: PostgreSQL for metadata store (required for multi-node, hybrid, and enterprise deployments)
  • Cache (optional): Redis for embedding cache and query result cache
Review Finding — Infrastructure Redundancy: The v1.1 spec defined per-node reliability (circuit breakers, health checks) but not cross-node redundancy. Production deployments should include: PostgreSQL primary/standby replicas (auto-failover), embedding service health checks with automatic failover (via load balancer health routing), and Redis Sentinel or cluster mode for the cache layer. The admin portal exposes dependency health at GET /admin/health so operators can verify redundancy status.

9. Secrets Management

Secrets are never hardcoded in Arcanum. All credentials, API keys, and tokens are loaded through the SecretStore trait at startup.

Secret Management Strategy:

  • Local Development: Environment variables (e.g., OPENAI_API_KEY, PGVECTOR_CONNECTION_STRING, JWT_SECRET)
  • Production: Cloud secrets manager (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager) — loaded via the SecretStore trait
  • Key Types: Embedding API keys, vector store connection strings, JWT signing keys, OAuth client secrets, Redis passwords, admin JWT secrets
  • Rotation: SecretStore supports hot-reload on configurable intervals; services can re-fetch secrets without restart
  • Logging: Secret values are never logged; only metadata (key path, source type) is recorded in audit logs
  • Admin Key Rotation: Admin portal exposes POST /admin/keys/rotate for rotating user API keys and admin JWT secrets

10. Reliability & Operational Considerations

Reliability is a first-class concern for all production deployment modes.

Graceful Degradation:

  • When vector store is unavailable: ingestion is queued in bounded queue for retry; retrieval returns a clear error (not a 500)
  • When embedding service times out: ingestion is queued; retrieval falls back to cached results if available
  • When metadata DB is unreachable: read operations may use cached collection metadata; writes are queued

Circuit Breakers:

  • Each external service boundary (embedding API, vector store, metadata DB) has an independent circuit breaker
  • Circuit states: closed (normal), open (fail fast), half-open (probe recovery)
  • Configuration: failure threshold, timeout, reset interval — all tunable via ArcanumConfig
  • Staggered reset: Randomized reset intervals (default 5-15 seconds jitter) prevent thundering herd in distributed deployments
  • Circuit breaker states are exposed via admin API: GET /admin/circuit-breakers

Health Checks:

  • Liveness probe (/health): Internal health — is the process running? (always returns 200 if process is alive)
  • Readiness probe (/ready): Dependency health — checks vector store connectivity, embedding service reachability, and metadata DB status
  • Readiness probe returns 503 if any critical dependency is unavailable; load balancers and orchestrators (Kubernetes, Docker) use this to route traffic and trigger restarts
  • Admin health endpoint (GET /admin/health) provides detailed dependency status for team monitoring

Operational Patterns:

  • Async ingestion via tokio-based worker pool — accepts requests synchronously, processes in background, returns OperationId for status tracking
  • Retry with exponential backoff and jitter for transient failures
  • Structured audit logging for all operations (ingestion, retrieval, admin) — includes user identity, collection, timestamp, and outcome
  • Real-time event streaming via WebSocket/SSE for ingestion progress, circuit breaker state changes, and health status
