1. Positioning & Design Principles

Arcanum is a high-performance Rust RAG knowledge engine framework. It handles the full knowledge lifecycle: ingestion, enrichment, indexing, and retrieval. It is the foundational knowledge layer for ArcVerse and integrates with any agent framework via the MCP protocol or HTTP/gRPC.

The Arcanum / ArcVerse Boundary
Arcanum owns: anything that uses models or ML to improve the quality, structure, or retrievability of knowledge — contextual enrichment, entity extraction, hierarchical clustering, retrieval fusion, quality evaluation.
ArcVerse owns: multi-step reasoning, tool use, memory management, task planning.
ArcVerse consumes RetrievalResult from Arcanum. It has no knowledge of how that result was produced.

Design Principles

  • Trait-driven, not inheritance-driven — every component is swappable
  • Library-first — usable as a Rust crate before it is a service
  • Named templates, composable internals — sensible defaults, full flexibility underneath
  • Measure everything — evaluation is first-class, not an afterthought
  • Provider-agnostic — local and cloud models, any vector store, any graph backend
  • Anti-corruption boundaries — external API types never leak past their crate

4.2 TextEnricher Intent Model

async fn enrich(&self, request: EnrichRequest) -> Result<EnrichedText>;

// EnrichRequest:
//   text:    content to enrich
//   intent:  ContextPrefix | Summarize | ExtractEntities | Caption | Rerank | Custom
//   context: optional title, section, adjacent chunks
Design Decision — TextEnricher vs LanguageModel: The trait is named TextEnricher because it describes the contract (text in → enriched text out), not the implementation. An LLM is one implementation. GLiNER handles ExtractEntities without an LLM. A future embedding model with generative capability could implement both Embedder and TextEnricher. The abstraction is future-proof.

4.3 Cross-Cache Invalidation Protocol

Defined here as a cross-module contract honored by both caches:

document modified
    → (1) EmbeddingCache: invalidate vector entries for that document's chunks
    → (2) QueryCache: invalidate entries for affected collections
Implemented as a single atomic operation in arcanum-pipeline.

arcanum-vector

All three components share the same ChunkId primary key space. HybridIndexManager coordinates VectorStore + BM25Index writes atomically during ingestion.

SQLite Restriction: Development and prototyping only. ArcanumEngine::build() rejects SQLite when runtime_mode = Production or Enterprise. Production requires PostgreSQL.

ColBERT multi-vector support: VectorStore accepts Vec<Vector> per chunk — token-level vectors for ColBERT stored as a payload alongside the primary dense vector. Backends without native multi-vector support serialize as a column with fallback to single-vector scoring.

arcanum-graph

arcanum-graph is a pure storage and traversal layer. It does not extract entities — that is arcanum-ingestion's job via TextEnricher. Each Entity carries Vec<ChunkId> linking back to source chunks, enabling GraphRetriever to return RetrievedChunk records that participate in fusion identically to vector results.

arcanum-tree — RAPTOR

RAPTOR Build Algorithm
flowchart LR

11. arcanum-pipeline

DAG execution engine. Owns no stage logic — that lives in arcanum-ingestion and arcanum-retrieval. Owns execution: ordering, parallelism, error recovery, progress tracking.

ComponentResponsibility
PipelineDAGDirected acyclic graph of Stage nodes and edges; independent stages run concurrently via tokio::join
StageExecutorRuns a single stage; wraps errors in StageError; records per-stage timing and output stats
IngestionWorkerTokio background task pool; drains BoundedQueue; executes pipeline DAGs; emits progress events
RetryPolicyExponential backoff with jitter; configurable max attempts, base delay, max delay; per-stage retry config
ArcanumPipelineRegistryMaps PipelineTemplate enum to pre-built DAG definitions; users register custom DAGs via register_pipeline()
Error Recovery: Core stage failure (Chunk, Embed, VectorWrite) → Failed → re-queued. Non-core stage failure (GraphWrite, TreeWrite) → PartialSuccess — recorded in IngestionReport, does not block other branches.

12. arcanum-eval

First-class evaluation layer. Not a test harness — a retrieval quality measurement system that runs against live or benchmark collections.

EvalReport includes strategy breakdown — which retrieval strategies contributed to hits. Used to tune FusionEngine weights and RetrievalConfig. Accessible via arcanum-engine service layer for external agents.

18. Security

Security is a first-class concern in Arcanum's design, especially when running as an MCP service exposed to external agents.

Authentication & Authorization

MechanismDetails
User API keysHMAC-signed; collection-scoped ACLs (allowed collections + operations + expiry)
Admin JWTRS256; short-lived (1 hour) + refresh token; three roles; completely separate from user API keys; never exposed via MCP
OAuth2 (optional)Enterprise SSO; IdP roles mapped to Arcanum RBAC roles
Collection ACLExplicit allow-list per collection; cross-collection queries require explicit multi-collection permission

Threat Model

ThreatMitigation
Prompt injection via document contentPreprocessor sanitizes before TextEnricher
Cross-tenant data leakageCollection-level ACL, VectorStore namespace isolation
Unauthorized admin accessAdmin JWT separate from user keys; IP allowlist option; admin endpoints not in MCP
Admin privilege escalationRBAC enforced in arcanum-engine; all admin ops audited
DoS / resource exhaustionBoundedQueue cap (503 + Retry-After); per-user rate limiting
Embedding API key exposureSecretStore trait; never logged; hot-rotatable
Stale retrieval resultsCross-cache invalidation protocol (EmbeddingCache → QueryCache)
Thundering herd on recoveryStaggered circuit breaker reset (5–15s jitter, seeded by node ID)

Encryption

In transit: TLS 1.3 mandatory for all external connections in Production and Enterprise; plaintext connections rejected at startup.
At rest: Mandatory for Production and Enterprise. pgvector: tablespace or column-level encryption. LanceDB: encrypted filesystem (no native support). Neo4j: encrypted storage. Redis 7+: encrypted persistence.

    Closed --> Open : failures exceed threshold
    Open --> HalfOpen : reset interval elapsed\n(5–15s jitter per node)
    HalfOpen --> Closed : probe succeeds
    HalfOpen --> Open : probe fails
    note right of Open : fail fast — no requests forwarded
    note right of HalfOpen : one probe request allowed

20. Secrets Management

Secrets are never hardcoded. All credentials, API keys, and tokens are loaded through the SecretStore trait at startup and hot-reloaded on rotation. Secret values never appear in logs or audit trail.
EnvironmentSecretStore Implementation
Local developmentEnvSecretStore — environment variables (OPENAI_API_KEY, JWT_SECRET, etc.)
Production (AWS)AwsSecretsManagerStore
Production (HashiCorp)VaultSecretStore
Production (GCP)GcpSecretManagerStore

Hot reload: SecretStore re-fetches on configurable interval; services pick up rotated secrets without restart.
Key rotation: POST /admin/keys/rotate — audited, hot-applied.
Covered: embedding API keys, vector store connection strings, JWT signing keys, OAuth client secrets, Redis passwords, admin JWT secrets, graph DB credentials.
